## 1. 目的と要件

### 1.1 目的

終盤将棋の弱い部分を鍛えるため、ブラウザだけで完結する練習アプリを作る。将棋AIとの対戦、終盤局面の再現、そして指す前の自己点検を1つのアプリにまとめる。

### 1.2 必須要件

| # | 要件 |
|---|---|
| R1 | インターネットで公開されている将棋AIの定義ファイルを読み込み、そのAIと対戦できる |
| R2 | 読みの深さを設定することで、強さを設定できる |
| R3 | 各マスについて、自分と相手の駒の利き（攻撃が到達するマス）が可視化されて見える。利きの強さ（利いている駒の数）も分かる |
| R4 | kifファイルを読み込むことで終盤の盤面を再現し、そこから指せる（AIとの対戦も含む） |
| R5 | 自分の手を指すとき、意識すべきチェック項目を登録し、それを表示できる |
| R6 | R5の表示条件を設定できる（例：相手が飛車角を動かした時） |
| R7 | ブラウザで動く |

### 1.3 ユーザーの決定事項

| 項目 | 決定 | 補足 |
|---|---|---|
| kif再現後の扱い | **再現した局面からもAIと対戦できる** | 通常対局と同じエンジンを使う。練習モードと検討モードの両方が使える |
| ブラウザ構成 | **A**: 依存ゼロ。素のHTML + ES modules + WASM | ビルド不要 |
| 配信先 | **Firebase Hosting** | `firebase.json` の `headers` で COOP/COEP を設定する |
| エンジンの配置 | **同一オリジンに同梱**（`public/engine/`） | Worker が同一オリジンでないと動かないため、CDN からの読み込みは行わない |
| データの保存 | **端末内のみ**（localStorage） | 棋譜は保存しない。チェック項目だけ保存する |
| Firebase プロジェクト | **新規に作成する** | 作成はユーザーの Google アカウントで行う |
| チェック項目の表示タイミング | **指す前のみ** | 駒を掴んだ時に判定し、確認してから指す |
| 利きの表示 | **両サイド常時表示**（既定ON） | 表示の切り替えも用意する |
| 自駒がいるマスの利き | **数える**（守りの強さとして表示） | 飛び駒は最初にぶつかった駒のマスまで数えて止まる |
| 通常対局のモード | 練習モードと検討モードを切り替え可能 | 検討モードでは評価値・候補手を出す |

**モードの定義**

- **練習モード**: 人間の手番では評価値・候補手・読み筋を隠す。本番と同じ感覚で指すためのモード。
- **検討モード**: 人間の指し手を待たず、その場でAIに局面を解析させる。評価値・候補手を一覧表示し、手を戻して別の指し手を試せる。

この2モードは、**通常対局（初期局面から始める場合）と kif から再現した局面の両方**に適用する。kif の局面でも、練習モード（評価値を隠してAIと対戦）と検討モード（評価値と候補手を表示）を切り替えられる。

## 2. 技術検証結果

本仕様の技術的前提は、すべて**ブラウザ実機で検証済み**である。推測は含まない。

### 2.1 採用エンジン

`fairy-stockfish-nnue.wasm`（npmパッケージ `fairy-stockfish-nnue.wasm`、バージョン 1.1.12、ライセンス GPL-3.0）からエンジンの3ファイルを取得し、アプリに同梱して配信する（附録C）。

| 検証項目 | 実測結果 |
|---|---|
| 将棋モード | `setoption name UCI_Variant value shogi` で動作 |
| 探索 | `go depth 8` → `bestmove c3c4 ponder b8c8`（0.23秒 / 8,092 nodes / 35,491 nps） |
| 深さ指定 | `info depth N …` が深さごとに出力される |
| 評価値 | `score cp N` の形式で出力される |
| 候補手 | `MultiPV` で複数候補。最大300まで指定可 |
| 合法手の列挙 | `MultiPV` を大きくして低い深さで探索すると全合法手が得られる |
| 並列探索 | `Threads` が 1〜512。pthread ビルド |
| 起動時の入出力 | `uci` で `uciok`、`isready` で `readyok` |

### 2.2 起動条件（決定的な制約）

```
crossOriginIsolated = false → ReferenceError: SharedArrayBuffer is not defined → 起動失敗
crossOriginIsolated = true  → 正常起動
```

配信側に次のヘッダーが必須である（実測で検証済み）。

```
Cross-Origin-Embedder-Policy: require-corp
Cross-Origin-Opener-Policy: same-origin
```

配信先は Firebase Hosting とし、`firebase.json` の `headers` で設定する（詳細は附録C）。

**エンジンは同一オリジンに置く。** COEP `require-corp` の下では `crossorigin` 属性のないクロスオリジンの `<script>` がブロックされる。さらに決定的なのは、**`new Worker()` がクロスオリジンの URL を受け付けない**ことである。このエンジンは pthread ビルドで内部から `stockfish.worker.js` を Worker として読み込むため、ワーカースクリプトが同一オリジンにないと動かない。したがってエンジンの3ファイル（`stockfish.js`、`stockfish.wasm`、`stockfish.worker.js`）は `public/engine/` に同梱して配信する。

**重要**: 素の `python3 -m http.server` はこのヘッダーを送らないため、開発中もエンジンが起動しない。ヘッダーを付与する専用の開発サーバースクリプト（`serve.py`）を用意する。

### 2.3 採用しなかったライブラリ

**`ffish-es6` は使用しない。** 実測でビルドが壊れていることを確認した。

| 検証項目 | 実測結果 |
|---|---|
| `variants()` | 空文字（`shogi` が含まれない） |
| `push("7g7f")` | `false` を返す（先手の合法手のはず） |
| `pop()` | `RuntimeError: memory access out of bounds` |

教訓: `ffish.d.ts`（型定義）だけを読むと「使えるAPIが揃っている」と誤認する。**必ず実挙動を検証すること。**

この結果を受け、合法手の生成と局面の進行はエンジン（USIコマンド）に一本化する。自前で書くのは利きの可視化だけにする。

### 2.4 座標系（実測で完全確定）

エンジンの指し手の書式は次のとおり。

| 種別 | 書式 | 例 |
|---|---|---|
| 盤上の移動 | `<移動元><移動先>` | `c3c4` |
| 駒打ち | `<駒種>@<マス>` | `P@e5` |
| 成り | 末尾に `+` | `e6e7+` |

**FEN と エンジン座標の対応**

検証は3通り独立に行い、すべて一致した。

1. 四隅と中央に駒を1つだけ置いた局面で、その駒の移動元をエンジンに尋ねる

| FEN の位置 | 書いた FEN | 返った移動元 |
|---|---|---|
| 1段・1列 | `k8/9/…` | `a9` |
| 1段・9列 | `8k/9/…` | `i9` |
| 9段・1列 | `…/k8` | `a1` |
| 9段・9列 | `…/8k` | `i1` |
| 5段・5列 | `…/4k4/…` | `e5` |

2. 初期局面の合法手が **30手**（将棋の正しい値）。内訳も一致（歩9、香2、銀4、金6、玉3、飛6）。
3. 先手の飛車（2八）が `h2` となり、その移動が `h2c2 … h2g2` と `h2i2` の6手。8八の角で止まることも一致。

**変換式（確定）**

```
行の並び          : 9列 → 1列 の順（標準SFEN）
FENの行          : 1行目が1段、9行目が9段
大文字 / 小文字    : 大文字 = 先手（手番 'w'）、小文字 = 後手

engineFile (a..i) = "abcdefghi"[行内インデックス]   // 0 → a（9列）、8 → i（1列）
engineRank (1..9) = 10 - 段番号                     // 1段 → 9、9段 → 1
```

逆変換は次のとおり。

```
段番号       = 10 - engineRank
行内インデックス = "abcdefghi".indexOf(engineFile)
```

**座標の検算**

| 駒 | 実際の位置 | FEN上の位置 | エンジン座標 |
|---|---|---|---|
| 先手の玉 | 5九 | 9行目・5列 | `e1` |
| 先手の飛 | 2八 | 8行目・2列 | `h2` |
| 後手の玉 | 5一 | 1行目・5列 | `e9` |
| 後手の飛 | 8二 | 2行目・8列 | `b8` |

**kif → エンジン座標の変換**

kifの指し手は「列の数字＋段の漢数字」で書かれる（例: `７六`）。変換は座標系から自動的に決まる。

```
engineFile = "abcdefghi"[9 - kifの列番号]
engineRank = 10 - kifの段番号（漢数字を数値に）
```

**変換の検算（エンジンの実測値と一致）**

| kif表記 | 変換後 | エンジンの実測 |
|---|---|---|
| `７六歩(77)`（先手） | `c3c4` | 初期局面の最善手が `c3c4` と一致 |
| `３四歩(33)`（後手） | `g7g6` | 上記の読み筋に `g7g6` と出力 |

この2手（▲７六歩 △３四歩）は読み筋 `c3c4 g7g6` としてエンジンが実際に出力した手順である。座標変換が最初から最後まで通っていることを、この一致が示している。

**注意**: `position fen …` に渡すFENはこの向きのものをそのまま使う。自前の変換は「画面表示 ↔ エンジン記法」と「kif表記 ↔ エンジン記法」の間だけで行う。

### 2.5 評価関数の限界（正直な記載）

実測で、探索開始時に `info string classical evaluation enabled` が出力された。このブラウザビルドにはNNUEの評価ファイルが埋め込まれておらず、`EvalFile` が空のため**手書きの古典評価関数で動作する**。

したがって、次の点を利用者に明示する。

- 同じ深さでも、ネイティブ版のNNUEエンジンより明確に弱い。
- `go depth N` による強さ設定は機能するが、強さの上限はブラウザ実行の範囲に収まる。
- 本アプリの目的は終盤の練習であり、絶対的な強さは主目的ではない。

将来、NNUE評価ファイルを入手できた場合は、これも同梱して `EvalFile` に渡すことで強化できる。これはスコープ外とする。

### 2.6 任意局面の読み込み（kif局面から対戦するため）

kifから再現した終盤局面でAIと対戦するためには、任意の局面をエンジンに読み込ませる必要がある。以下を実測で確認した。

| 検証項目 | 実測結果 |
|---|---|
| 持ち駒の読み込み | 飛車を持たせると84手（玉5＋打79）、持ち駒なしは5手。打ち手が正しく生成される |
| 持ち駒つきの perft | 歩持ちの局面で 70 nodes（玉5＋歩1＋打64 と一致） |
| 二歩の制限 | 同じ列に自分の歩があると、その列への歩打ちが生成されない |
| 最終段の制限 | 歩を最終段に打つ手が生成されない |
| 局面の同一性 | `position fen <FEN>` と `position startpos moves <手列>` が **perft 3 で 54375 nodes と完全一致** |
| 決定性 | ハッシュクリア後は同一局面で同一の bestmove とスコアが返る |

**採用する読み込み方法**: kif適用後の局面から**SFENを組み立てて `position fen <SFEN>` で渡す**。持ち駒・成駒・手番を含めて1つの経路で扱えるため。平手の初期局面から始まる場合は `position startpos moves <手列>` でも同一の局面になることは perft で確認済みだが、分岐を減らすため SFEN 経由に統一する。

**SFEN の組み立て規則**（実測で確認した書式）

- 盤面は9行、1行目が1段、行内は9列→1列。成駒は `+` を前置。
- 持ち駒は `[` `]` で囲む。空なら `[-]`。
- 持ち駒の並びは SFEN の慣例（飛・角・金・銀・桂・香・歩、先手を大文字・後手を小文字）。同じ種類は枚数を数字で前置する（例: `[2R2B]`）。
- 手番は先手が `w`、後手が `b`。

**perft の利用**: エンジンは `go perft N` に対応している（実測）。ノード数は局面だけで決まるため、**局面を正しく読み込めたかの決定的なテスト**に使える。kifパーサの検証にも使う。

## 4. 機能仕様

### 4.1 R1/R2: エンジン対戦と強さ設定

#### エンジンの読み込み

同一オリジンの `engine/stockfish.js` を `<script>` で読み込む（`public/engine/` に同梱。附録C）。CDN や他のオリジンからは読み込まない。

読み込みに失敗した場合は「エンジンを読み込めませんでした」と画面に表示し、`public/engine/` に3ファイルが揃っているかを確認する手順を示す。

`crossOriginIsolated` が `false` の場合は、エンジンの読み込みを試みる前に警告を表示する。「このアプリは COOP/COEP ヘッダーが必要です。ホスティングの設定を確認してください」。

#### 初期化シーケンス（実測済みの手順）

```
uci
  → uciok を待つ
  → setoption name UCI_Variant value shogi
  → setoption name Threads value <N>
  → isready → readyok を待つ
```

`Protocol` という option は存在しない（設定すると `No such option: Protocol` が返る）。将棋にするかどうかは `UCI_Variant` だけで決まる。

#### 強さ設定UI

| コントロール | USI option / 値 | 範囲 | 既定 |
|---|---|---|---|
| 読みの深さ | `go depth N` の N | 1〜40 | 10 |
| Skill Level | `Skill Level` | -20〜20 | 20 |
| Elo制限 | `UCI_Elo` | 500〜2850 | 1350 |
| Elo制限の有効化 | `UCI_LimitStrength` | check | false |
| 探索スレッド | `Threads` | 1〜min(8, `hardwareConcurrency`) | 2 |
| ハッシュ | `Hash`（MB） | 16〜256 | 64 |
| 複数候補 | `MultiPV` | 1〜10 | 1 |

**使い分けのルール**

- 深さ指定を主軸にする（要件R2）。この場合、`UCI_Elo` と `UCI_LimitStrength` は無効にする。
- 弱い相手と指したい場合は、`UCI_LimitStrength` を有効にして `UCI_Elo` を指定し、`go movetime <ms>` で時間制限を渡す。この場合は深さ指定と併用しない。

UIではこの2つをラジオ選択で切り替える（「深さ指定」／「Elo指定」）。両方を同時に有効にできる状態を作らない。

`Hash` を256MBに制限するのは、WASMのメモリが有限で、大きい値では確保に失敗するため。

#### 対局の流れ

1. 人間が駒を掴む。行き先の候補を `moves.js` がエンジン照合で確定する。
2. チェック項目の確認（該当があれば確認パネルを出す）。
3. 指す。局面を更新し、利きを再計算する。
4. AIの手番: `position fen <現在局面> moves <手履歴>` を送り、`go depth N` で探索する。
5. `bestmove` を盤面に適用し、AIの指し手を棋譜に追加する。
6. 終局は、エンジンが `bestmove` を返さない、または投了を示す値を返した場合として扱う。具体的な戻り値は節2.6のとおり実装時に実測して確定する。自前で詰み判定を書かない。

ポンダー（相手番での先読み）は実装しない。1手ごとの応答性のほうが練習では重要であり、複雑さに見合わないため。

### 4.2 R3: 利きの可視化

#### 自前実装の理由

`ffish-es6` が壊れているため、利きの計算は自前で実装する。エンジンが返すのは合法手であり、利きとは別の概念である。たとえば自駒がいるマスは合法手にはならないが、そこに利いている駒の数は守りの強さとして重要である。したがって自前実装が必要になる。

#### 計算アルゴリズム

盤面配列（81マス）を受け取り、先手と後手それぞれについて、**81マスごとの利き数**（そのマスに利いている駒の数）を数える。単に「利きがあるかないか」ではなく、数えることが要件である。

各駒の攻撃パターンを生成し、飛び駒は進行方向に進める。最初にぶつかった駒のマスまでを数え、そのマスより先へは伸ばさない。ぶつかった駒が自駒でも敵駒でも、そのマスは数える（ユーザー確認済み）。自駒なら「守っている」、敵駒なら「取れる」という意味になる。

このため、同じマスに複数の駒が利くと利き数は2以上になる。たとえば守りの駒が2枚あるマスは「自分の利き2」になる。

| 駒 | 攻撃が到達するマス |
|---|---|
| 歩 | 前方1マス |
| 香 | 前方のみ直線 |
| 桂 | 前方2マス＋左右1マス（跳び。2マス） |
| 銀 | 前方1マス＋斜め4マス（合計5マス） |
| 金 | 前方1・斜め前方2・左右1・後方1（合計6マス） |
| 玉 | 周囲8マス |
| 角 | 斜め4方向の直線 |
| 飛 | 縦横4方向の直線 |
| と（歩の成り） | 金と同じ（6マス） |
| 成香・成桂・成銀 | 金と同じ（6マス） |
| 馬（角の成り） | 斜め4方向の直線＋縦横4方向に1マス |
| 龍（飛の成り） | 縦横4方向の直線＋斜め4方向に1マス |

金と玉は成らないので、成りの行は設けない。後手の駒は前後が逆になる。先手は段番号が小さくなる向き、後手は段番号が大きくなる向きが「前」である。

#### 表示仕様（ユーザー指定）

表示の実例は `docs/mockups/attack-map-preview.html` にある（設計確認用のモックアップ。利き数は実際に計算している）。

**利き数の数字**

- 各マスの**左上**に、相手の利き数を小さな赤い数字で表示する。
- 各マスの**右下**に、自分の利き数を小さな青い数字で表示する。
- 利き数が0のマスには数字を表示しない。
- 数字は駒の文字より小さくし、駒の表示を邪魔しないようにする。

**背景の濃さ**

マスの背景を利き数に応じて塗る。利き数が多いほど濃くする。

| 利き数 | 背景の不透明度 |
|---|---|
| 0 | 塗らない |
| 1 | 0.15 |
| 2 | 0.30 |
| 3 | 0.45 |
| 4 | 0.60 |
| 5以上 | 0.75 |

不透明度は1か所の定数としてまとめ、実際の見た目を見て調整できるようにする。上限を0.75とするのは、濃くしすぎると駒の文字が読めなくなるためである。駒の文字は背景の上に描画し、必要に応じて駒の面に薄い下地を敷いて読みやすさを保つ。

**両方の利きがあるマスの分割**

1つのマスに自分と相手の利きが両方ある場合は、マスを**斜めに2分割**して塗る。

- 左上の三角形: 赤（相手）。濃さは相手の利き数。
- 右下の三角形: 青（自分）。濃さは自分の利き数。

分割の向きは数字の位置と対応させる（左上=相手の数字、右下=自分の数字）。これにより、どちらの三角形がどちらの数字に対応するかが位置で分かる。

**その他**

- 自分の利きだけのマスは青一色、相手の利きだけのマスは赤一色で塗る。
- 守られているかどうかは、そのマスの青い利き数で分かるため、駒に特別な印は付けない。
- 実際に指せるマス（合法手）は、利きとは別の表現（点滅する枠など）で示す。利きの中に混ぜない。
- 表示は「両方」「自分のみ」「相手のみ」「なし」の4通り。既定は「両方」。「自分のみ」では赤の三角形と相手の数字を描かない。
- 駒を掴んで行き先を選んでいる間は、選んだ駒を強調しつつ利きの表示は残す（利きを見ながら指し手を決められるようにするため）。
- AIの手番中は利きの表示を消す（盤面が読みにくくなるため）。

利きは盤面が変わるたびに再計算する。81マス×2サイドなので計算量は小さく、毎回の再計算で問題ない。

### 4.3 R4: kifファイルの読み込み

#### kif形式の構造

```
開始日時：2026/10/03
手合割：平手
先手：
後手：

後手の持駒：桂馬 二 銀 一
先手の持駒：なし

   1 ７六歩(77)   ( 0:01/00:00:01)
   2 ３四歩(33)   ( 0:00/00:00:01)
   3 ２二角成(88)
   4 同　銀(31)
   5 ５五銀打
   6 投了
```

指し手の要素は次のとおり。

- 手数
- 移動先マス（例: `７六`）。直前の手と同じマスなら `同`。
- 駒種（`歩` `香` `桂` `銀` `金` `角` `飛` `玉` と、すでに成っている駒の `と` `成香` `成桂` `成銀` `馬` `龍`）
- 成りの指定（`成` または `不成`）
- 移動元（`(77)` の形式。盤上の移動のみ）
- 駒打ちの指定（`打`。この場合は移動元がない）
- 消費時間（括弧内。解釈しない）

#### パーサ仕様

1. ヘッダ行（`開始日時` `終了日時` `棋戦` `手合割` `先手` `後手` `下手` `上手` `場所` `持ち時間` など）を読み飛ばす。
2. `先手の持駒：` と `後手の持駒：` の行から、初期局面の持ち駒を取得する。駒名は `歩` `香` `桂` `銀` `金` `角` `飛` と、その個数（漢数字または算用数字）。
3. 盤面図（`|` と `+---` で描かれた行、および列番号の行）があれば読み飛ばす。盤面図のみから局面を作ることはしない。
4. 以降の行を指し手としてパースする。
   - 全角数字（`１`〜`９`）を半角に変換する。
   - 段は漢数字（`一`〜`九`）で表される。列は数字である。
   - 移動先マスと駒種を分離する（例: `７六歩` → 7六へ歩）。
   - `同` は直前の手の移動先と同じマスとして解決する。盤面の状態から推測しない（直前の手のマスをそのまま使う）。
   - `(77)` の移動元があれば、そのマスと移動先マスの2マスで指し手を作る。移動元が省略されている場合は、そのマスへ動ける同じ駒種の駒を盤面から探して特定する。
   - `打` が付いていれば駒打ちとして `P@e5` の形式にする。
   - `成` が付いていれば末尾に `+` を付ける。`不成` は付けない。
5. 変換した手列を、エンジンへ1手ずつ `position … moves …` で適用する。
6. 次の表記で読み取りを終了する（`投了` `中断` `詰み` `千日手` `持将棋` `切れ負け` `反則負け` `入玉勝ち` `宣言勝ち`）。
7. 変化（`変化：N手`）が現れたら、それ以降は本譜ではないため読み飛ばす。

#### 終盤の再現と、そこからの対戦

- kifを最後まで適用し、**最終局面を開始局面として**提示する。
- 「何手目から」を選べるようにする（スライダー、または一手ずつ前後に動かすボタン）。既定は最終局面。
- その局面から**AIと対戦できる**。通常対局と同じエンジンを使い、**練習モード**（評価値を隠す）と**検討モード**（評価値と候補手を表示）の両方が使える。
- `state.js` の手履歴により、読み込み後も手を戻せる（開始局面まで戻れる）。

**自分が指す側の決定**

- 既定は「再現した局面の手番側を自分が指す」。終盤の練習では、次に指す側の判断を鍛えたい場面が多いため。
- 先手・後手の切り替えを用意する。自分が後手を選び、局面の手番が先手なら、**AIが先に指してから**自分の手番になる。
- チェック項目の条件式でいう「相手」は、**AIが指す側**（自分の反対側）を指す。

**エンジンへの局面の渡し方**

kifを適用した結果の局面から**SFENを組み立てて `position fen <SFEN>` で渡す**（節2.6）。持ち駒・成駒・手番を含めて1つの経路で扱える。読み込んだ後に `go depth N` を送れば、その局面からAIが指す。

**局面を正しく渡せたかの確認**

エンジンは `go perft N` に対応している（節2.6）。読み込んだ局面の perft ノード数を記録しておき、異常があれば画面に警告を出す。黙って別の局面で対局が始まることを防ぐ。

#### エラー処理

- 解釈できない行は、行番号とその行を示してスキップし、処理は続ける。最後に「何手読み取れたか」を報告する。
- エンジンが指し手を合法手として受理しなかった場合は、その手に印を付けて表示し、以降の局面構築を止める。黙って誤った局面を表示しない。

### 4.4 R5/R6: チェック項目

#### データ構造（localStorageに保存）

```json
{
  "id": "uuid",
  "text": "相手の飛車と角の利きを確認する",
  "condition": { "type": "opponentMovedPiece", "piece": "rook_bishop" },
  "enabled": true,
  "priority": "high"
}
```

#### 条件式

| type | 意味 | パラメータ | 例 |
|---|---|---|---|
| `always` | 常に成立 | なし | 毎手で確認する |
| `opponentMoved` | 相手が何かを動かした直後 | なし | |
| `opponentMovedPiece` | 相手が指定の駒を動かした | `piece` | `rook`（飛）、`bishop`（角）、`rook_bishop`（飛車角） |
| `opponentMovedFrom` | 相手が指定のマスから動かした | `squares` | `["9a","9b","9c"]` |
| `opponentMovedTo` | 相手が指定のマスへ動かした | `squares` | `["1a","1b","1c"]` |
| `opponentInCheck` | 相手に王手をかけている | なし | |
| `myKingThreatened` | 自分の玉が相手の利きに入っている | なし | `attack-map.js` を再利用する |
| `myPieceAt` | 自分の指定の駒が指定のマスにある | `piece`, `squares` | `["9g","8f"]` に飛 |
| `handHasPiece` | 自分の指定の駒が持ち駒にある | `piece` | 飛を持っている |
| `handCountAtMost` | 自分の持ち駒の総数が指定以下 | `count` | 10以下で終盤入り |
| `plyAtLeast` | 指定の手数以上進んでいる | `ply` | 60手以上 |

条件は「直前の相手の指し手」と「現在の盤面」から評価する。`opponentMoved*` 系は直前の手が必要なため、手履歴から取り出す。

`piece` の判定は成駒をどう扱うかを明示する。`rook` は龍を含み、`bishop` は馬を含む。`rook_bishop` は成っていない飛と角、および龍と馬のすべてを含む。ユーザーの例「相手が飛車角を動かした時」は `opponentMovedPiece` と `piece: "rook_bishop"` で表現できる。

`squares` を指定するパラメータの座標は、画面表示のマス名（kifと同じ「7六」の形式）で指定する。内部では `coords.js` でエンジン座標に変換して比較する。

#### 表示のタイミング（ユーザー指定: 指す前のみ）

1. 人間が駒を掴む。
2. 行き先の候補を `moves.js` がエンジン照合で確定する。
3. チェック項目を評価し、該当するものを集める。
4. 該当があれば確認パネルを表示する。
   - 「この手で確認すること」という見出し
   - 項目の一覧（チェックボックス付き。すべてチェックするまで「指す」を押せない）
   - 「この手をやめる」ボタン（必ず用意する。確認を避けたい場面のために必要）
5. 該当がなければそのまま指せる。

**同じ手で確認パネルを繰り返し出さない。** 一度確認して指した手について、同じ局面で再度パネルを出さない。相手の手が進めばリセットする。

#### 登録UI

パネルで次の操作ができるようにする。

- テキスト（自由記述）
- 条件タイプ（ドロップダウン）とパラメータ（条件タイプに応じて表示を変える）
- 優先度（高・普通・低）
- 有効・無効の切り替え
- 削除

初期状態の項目は用意しない。利用者自身が自分の課題を登録する。アプリ側が内容を決め打ちしない。

### 5.3 駒の表示

- Unicodeの文字（`歩` `と` `龍` など）によるテキスト駒。画像アセットを持たず、依存を増やさない。
- 後手の駒は180度回転して表示する（将棋の慣習）。
- タップ領域は44px以上を確保する。
- 利き数の数字（左上の赤と右下の青）は駒の文字より小さく描き、駒と重ならない位置に置く。
- 確定前に、選択中の駒を枠で強調し、行き先にドットを表示する。
- 成りの選択が必要な場合は、成る／成らないを選ぶ小さなダイアログを出す。

### 5.4 練習モードと検討モード

- **練習モード**: 評価値・候補手・読み筋を隠す。ヘッダには手番とAIの深さだけを出す。
- **検討モード**: 人間の指し手を待たずに探索を走らせ、評価値と候補手（`MultiPV` 5程度）を一覧表示する。手を戻して別の指し手を試せる。
- 検討モードでは人間の指し手を待たないため、終局まで進めるモードではない。手戻り（undo）を前提とする。
- この2モードは、初期局面から始めた対局でも、kifから再現した局面でも同じように使える。
- kifから再現した場合は、**自分が指す側（先手／後手）の切り替え**をヘッダに出す。局面の手番と自分が指す側が食い違う場合は、AIが先に指す。

## 6. テスト戦略

テストは2層に分ける。

- **単体テスト**: Node.js の組み込みテストランナー（`node --test`）を使う。**依存パッケージは0個**。`package.json` はテストの実行にだけ使い、配信物（`public/`）には含めない。`coords.js` と `attack-map.js` は DOM もエンジンも必要としないため、そのまま実行できる。
- **統合テスト**: ブラウザの実機で行う。エンジンの起動、対局、kif、チェック項目はブラウザでしか確認できない。

`node --test` が動くことは実測で確認済み（ES modules、`public/js/` 配下のモジュールを直接 import、npm 依存なし）。テストファイルは `public/` の外の `test/` に置く。

### 6.1 単体テスト（エンジン不要）

`coords.js` と `attack-map.js` はエンジンの読み込みを必要としないため、そのまま検証できる。

| 対象 | 検証内容 |
|---|---|
| 座標変換 | 四隅と中央で FEN → エンジンが `a9`、`i9`、`a1`、`i1`、`e5` を返す |

| 利き数（合算） | 同じマスに複数の駒が利くと数が合算される（2枚で守られたマスは2になる） |

| 利き数（成駒） | と・成香・成桂・成銀が金と同じ6マスになる |
| 利き数（後手） | 後手の歩の利きが、段番号が増える向きになる |
| 表示の濃さ | 利き数1と5で背景の不透明度が仕様の表どおりになる |
| マスの分割 | 両方の利きがあるマスで、左上が赤・右下が青の三角形になる |

| kifパーサ（SFEN） | 適用後の局面から組み立てたSFENを読み直すと、同じ局面に戻る |

| 条件評価 | 条件と局面の組み合わせを表で検証する |

### 6.2 統合テスト（ブラウザ実機）

| テスト | 合格条件 |
|---|---|
| エンジンの起動 | COOP/COEP の下で `bestmove` が返る |
| 初期局面の合法手 | **30手**（将棋の正しい値） |
| 対局 | 人間が指す → AIが応答する → 終局まで進む |
| 深さ設定 | 深さを上げると `info depth` の最大値が上がる |
| kifの読み込み | 実ファイルで終盤が再現され、そこから指せる |
| **kif局面からの対戦** | kifで再現した局面からAIと対局できる。SFEN経由で渡した局面のperftが期待値と一致する |
| 指す側の切替 | 自分が後手を選ぶと、AIが先に指してから自分の手番になる |
| チェック項目 | 登録 → 条件成立 → 指す前にパネルが出る |
| 確認の回避 | 「この手をやめる」で指さずに戻れる |
| ヘッダー未設定 | 起動前に明確な警告が出る |

## 7. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| COOP/COEP ヘッダーが未設定 | エンジンが起動しない | 起動前チェックで明示的な警告を出す。`firebase.json` の `headers` と、ローカル用の `serve.py` を用意する |
| Node.js が無い | デプロイできない | Homebrew で導入する（`brew install node`。20以上が必要）。導入前でも `serve.py` でローカル確認はできる |
| `firebase login` がブラウザ認証を要する | 自動化できない | 本人の操作が必要な唯一の手順として明示する。それ以外は自動で行う |
| WASM が約1.6MB | 初回の読み込みが遅い | `Cache-Control` を長めに設定する。ローディングを表示し、先に盤面を描画する |
| 評価が古典評価 | 強さが限定的 | 節2.5のとおり明記し、UIにも注記する |
| `Hash` の過大指定 | WASMメモリの確保に失敗 | 256MBに制限する。`navigator.deviceMemory` で端末に応じて既定値を変える |
| `Config` を誤るとヘッダーが付かない | エンジンが起動しない | デプロイ後に `curl -I` で `cross-origin-embedder-policy` を確認する手順を設ける |
| タッチ端末での誤操作 | 意図しない駒を動かす | タップ領域を44px確保する。駒の選択と行き先の指定を2段階にする |
| kifの非標準な表記 | パースに失敗する | 行番号付きのエラー表示でスキップし、処理を続ける |

## 附録C: Firebase Hosting への配信

### C.1 必須ヘッダー（最優先）

```
Cross-Origin-Embedder-Policy: require-corp
Cross-Origin-Opener-Policy: same-origin
```

`firebase.json` に次のように書く。`source` は `**` で全ファイルに適用する。

```json
{
  "hosting": {
    "public": "public",
    "ignore": ["firebase.json", "**/.*", "**/node_modules/**"],
    "headers": [
      {
        "source": "**",
        "headers": [
          { "key": "Cross-Origin-Embedder-Policy", "value": "require-corp" },
          { "key": "Cross-Origin-Opener-Policy", "value": "same-origin" }
        ]
      }
    ]
  }
}
```

`public` は `public` ディレクトリを指定する（3.1 の構成に対応）。

### C.2 エンジンは同一オリジンに置く

`public/engine/` に次の3ファイルを同梱する。CDN からは読み込まない。

- `stockfish.js`
- `stockfish.wasm`（約1.6MB）
- `stockfish.worker.js`

理由は節2.2に書いたとおり。COEP 下でクロスオリジンのスクリプトがブロックされることに加え、`new Worker()` がクロスオリジンの URL を受け付けないため、ワーカースクリプトは同一オリジンでなければならない。

WASM は約1.6MBあるため、`Cache-Control` を長め（例: `max-age=31536000, immutable`）に設定して2回目以降の読み込みを速くする。

### C.3 デプロイに必要なもの

**Node.js（バージョン20以上）** が必須。`firebase-tools` の `engines` は実測で `>=20.0.0 || >=22.0.0 || >=24.0.0`。

```
HOMEBREW_NO_AUTO_UPDATE=1 brew install node
node -v
```

**手順**

```
# 1. ログイン（ブラウザが開く。ユーザーの Google アカウントで認証する）
npx firebase-tools login

# 2. プロジェクトを作成（初回のみ）
npx firebase-tools projects:create <project-id> --display-name "将棋鍛錬アプリ"

# 3. プロジェクトIDを設定
#    .firebaserc に { "projects": { "default": "<project-id>" } } を書く

# 4. デプロイ
npx firebase-tools deploy --only hosting
```

`firebase login` はブラウザでの認証が必要なため、**ユーザー本人の操作が要る**。それ以外は自動で実行できる。

### C.4 ローカルでの確認

- **Node あり**: `npx firebase-tools emulators:start --only hosting`（`firebase.json` のヘッダーが適用される）
- **Node なし**: `python3 serve.py`（COOP/COEP を自前で付与する。Node を入れる前でも確認できる）

素の `python3 -m http.server` はヘッダーを送らないため、エンジンが起動しない。
